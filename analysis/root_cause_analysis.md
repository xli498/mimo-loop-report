# MiMo Degenerate Loop — Evidence-Bounded Analysis

## Executive Summary

在一组历史日志及其当时的 `xiaomimimo/mimo-v2.5-pro` 配置中，观察到 `reasoning=True` 同时出现退化循环。样本量不足以估计总体概率，也不足以证明模型内部机制。本文严格区分历史观察、可复现实验、工程止损和待验证假设。

## 历史观察（不可外推）

| 指标 | 历史样本记录 | 边界 |
|------|------|------|
| 循环观察比例 | 约 30% | 不是总体故障率 |
| 重复次数 | 8–11 次 | 单一记录窗口 |
| 总持续时间 | 约 6 分钟 | 依赖当时网关与请求设置 |
| 每次间隔 | 约 33 秒 | 不代表所有运行 |
| 输出语言 | 英文 | 样本没有持续遵守中文指令 |
| 工具调用 | 0 次 | 仅该样本 |
| 参数 | `frequency_penalty=1.0`、`temperature=0.7` | 不代表参数在其他任务中无效 |

历史样本呈现以下序列：中文正常输出 → 中文尝试工具调用 → 多次重复英文输出。该序列可说明该次响应未稳定遵守中文约束；不能据此断言模型“忽略”了 System Prompt，或内部存在固定英文推理路径。

## 可复现层

`reproduce/test_loop_reproduce.sh` 用固定提示词、显式 `reasoning` 开关与检测规则记录结果。它是观察工具，不是概率估计器：

- 运行前须提供 `MIMO_API_KEY`，且不得提交响应、授权头或私有提示词；
- 结果应记录模型版本、端点、时间、请求上限和样本数；
- 出现循环只证明该次配置下的输出命中检测规则；未出现循环也不能证明不存在风险；
- 不要将单次脚本结果写成跨版本、跨端点或跨任务的模型结论。

## 待验证机制假设

以下解释没有 logits、供应商内部遥测或架构文档支撑，均是实验假设：

1. `reasoning=True` 可能改变了生成路径；是否存在独立推理引擎、其语言偏好为何，未知。
2. 某些任务结构可能与重复输出相关；“吸引子盆地”“固定点”等只是描述性模型，不是已证实根因。
3. 温度、频率惩罚、上下文长度和 System Prompt 可能影响结果；现有历史样本不能量化其因果效果。

后续实验应一次只变化一个因素，使用足够样本，并将“观察到的比例”与“置信区间/样本限制”一并报告。

## 工程侧止损

| 措施 | 能做什么 | 风险与验收 |
|------|----------|------------|
| 请求超时 | 在支持该限制的运行器中限制等待时间 | 可能截断正常长任务；验证超时实际生效 |
| 输出上限 | 限制单次响应体量 | 可能截断完整答案；验证实际 stop reason |
| 输出模式检测 | 发现已定义的重复模式 | 可能误报或漏报；用脱敏 fixture 回归 |
| 幂等与人工复核 | 限制重复副作用的影响 | 不能替代业务级结果判断 |

这些措施用于限制影响范围，并不“修复模型”。不要把固定参数值当作所有模型、端点或任务的通用处方。

## 结论

历史日志表明循环与 `reasoning=True` 同时出现；任何固定点、注意力或英文推理机制都仍是假设。当前可靠做法是：保留证据边界，使用请求上限与输出检测做工程止损，并在目标版本和目标任务上独立验证。
